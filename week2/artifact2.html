How the exam asks this

Hardening and management questions follow four reliable patterns.

Pattern 1: the SSH checklist, in order

Hostname and ip domain-name first (the RSA keys are named from them), then crypto key generate rsa (modulus 1024 or higher for SSH v2), a local user created with username admin secret ..., and on the vty lines: login local plus transport input ssh. Enforce the modern protocol with ip ssh version 2.

Trap: trying to generate keys before the domain name exists. The router literally refuses, and the exam knows it.

Pattern 2: the password hierarchy

enable secret stores a hash and always takes precedence over enable password, which stores plaintext. service password-encryption applies weak, reversible type 7 obfuscation to plaintext passwords: better than nothing, nowhere near a real hash. For local users, username ... secret beats username ... password for the same reason.

Trap: "service password-encryption makes passwords secure." It does not. It stops shoulder-surfing, not attackers. The secure options are the secret commands.

Pattern 3: SNMP versions and community strings

SNMPv2c authenticates with plaintext community strings: read-only (RO) and read-write (RW). SNMPv3 adds real authentication and encryption, which is its exam-tested advantage. The defaults public and private are known to every attacker on earth.

Trap: a config with snmp-server community public RW is a double fail: a well-known string AND write access. Flag both.

Pattern 4: copy commands read left to right

copy running-config tftp copies FROM the running config TO the server: a backup. copy tftp running-config is the restore. Same logic for startup-config: copy running-config startup-config is the everyday save. Source first, destination second, always.

Trap: reversed copy commands among the options. Read them left to right as "from, to" and the trap disappears.
